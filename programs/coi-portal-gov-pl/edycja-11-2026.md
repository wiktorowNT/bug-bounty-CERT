## Zasady testowania (§6)
1. Testy bez logowania albo **wyłącznie na własnych kontach (poza domenowymi) lub testowych**. Zakaz korzystania z cudzych kont.
2. Narzędzia automatyczne dozwolone, **maksymalnie 5 req/s**.
3. Zakaz DoS/DDoS, testów obciążeniowych i spamu (masowe maile/SMS-y/powiadomienia).
4. Naruszenie zasad może skutkować odrzuceniem zgłoszenia, a rażące naruszenie wykluczeniem z konkursu.

## Co jest nagradzane (§8.1), w skrócie
RCE · przejęcie konta (reset hasła, kradzież sesji/tokenu, logowanie bez hasła, podszycie się) ·
dostęp do danych wrażliwych / PII · SQLi · SSRF (odczyt sieci wewnętrznej, nie tylko DNS) · SSTI ·
file upload (RCE, obejście MIME/rozszerzeń) · XSS (poza wyłączeniami) · IDOR/BAC · eskalacja uprawnień ·
podatności API (brak autoryzacji, ukryte endpointy) · mass assignment · CORS z realnym odczytem danych ·
path traversal/LFI/RFI · CSRF z realnym wpływem · open redirect **tylko** w łańcuchu (OAuth/OIDC, bypass CSP,
udokumentowany phishing) · subdomain takeover z PoC · web cache poisoning · HTTP request smuggling · XXE.

Słabsze problemy z sesją (brak rotacji, brak wygasania, domyślne dane logowania o niskich uprawnieniach)
są „informacyjne lub nisko nagradzane według uznania”.

## Co NIE jest nagradzane (§8.2), najczęstsze pułapki
- brak nagłówków bezpieczeństwa, HSTS, flag ciasteczek, captchy; SPF/DKIM/DMARC; TLS i certyfikaty;
- ujawnianie wersji, stack trace, IP, ścieżek; **user enumeration**; endpointy debugowe bez eskalacji;
- self-XSS, czysty HTML injection, content injection, clickjacking bez krytycznej akcji, tabnabbing;
- CSRF na logout lub akcjach read-only; open redirect bez łańcucha; **blind SSRF potwierdzony tylko przez DNS**;
- brak rate limitingu bez scenariusza przejęcia konta; spam; DoS;
- znane CVE bez działającego PoC, przestarzałe biblioteki bez wpływu; wyniki skanerów bez ręcznej weryfikacji;
- klucze API bez możliwości nadużycia lub z ograniczeniem do domeny;
- ataki wymagające MITM, fizycznego dostępu, DevTools lub starych przeglądarek;
- **każde zgłoszenie bez PoC**.

## Wstępne obserwacje celu (pasywne, kilka pojedynczych zapytań)
- Portal treściowy: struktura `/web/<jednostka>/<artykuł>` (np. `/web/gov`, `/web/premier`, `/web/mswia`),
  setki serwisów ministerstw i urzędów w jednej domenie, więc **duża, jednorodna powierzchnia**.
- Wyszukiwarka: `/web/gov/szukaj` (formularz GET), naturalny cel dla reflected XSS i injection w parametrach.
- Frontend: jQuery 3.7.1, jQuery UI 1.13.2, Vue (vue-select 3.20.4), modaal, validate.js, własne `bundle-*.js`,
  `gov_context.js?locale=pl_PL` (parametr `locale` odbijany w JS, warto sprawdzić).
- Analityka: `matomo.www.gov.pl` (inna subdomena, **poza zakresem**). Linki zewnętrzne do `mobywatel.gov.pl`
  i `pomagamukrainie.gov.pl` są **poza zakresem**.
- Nagłówki: HSTS z preload, `X-Frame-Options: SAMEORIGIN`, `nosniff`, Permissions-Policy, **brak CSP** w odpowiedzi
  strony głównej (sam brak CSP nie jest nagradzany, ale ułatwia eksploatację XSS).
- `Cache-Control: max-age=600` na HTML, więc warstwa cache przed aplikacją: **kandydat do web cache poisoning /
  cache deception** (unkeyed headers typu `X-Forwarded-Host`, `X-Original-URL`, parametry).
- `robots.txt` to przekierowanie do `/static/code/robots.txt` z treścią `Allow: /`, bez ukrytych ścieżek.
- Seria szybkich zapytań o pliki JS kończyła się `connection reset`: przed aplikacją działa WAF lub rate limiting.
  Trzeba **trzymać się wyraźnie poniżej 5 req/s** i nie wysyłać zapytań równolegle.

## Strategia: gdzie szukać
1. **Wyszukiwarka i parametry GET** (`szukaj`, filtry, paginacja, `locale`): reflected i DOM XSS
   (brak CSP, jQuery i Vue: sprawdzić template injection po stronie klienta `{{ }}`).
2. **Cache poisoning / deception**: HTML jest cache'owany 10 min, więc sprawdzić, które nagłówki wpływają na odpowiedź,
   ale nie są częścią klucza cache. Za trwałe zatrucie strony gov.pl można dostać high/critical.
3. **Formularze z uploadem** (kontakt, zgłoszenia, wnioski w serwisach ministerstw), obejście MIME i rozszerzeń.
